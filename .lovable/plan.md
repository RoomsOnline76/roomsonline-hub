# Partner / affiliate perks on a property

Today the only voucher surface in property setup is **Specials → Vouchers**, which manages `promo_codes` — discount codes that reduce the guest's own booking total at checkout. That is the wrong instrument for an affiliation perk: a partner offer (wine tasting, spa treatment, restaurant credit, tour discount) must not discount the stay, and it should only be revealed once the booking is paid.

So a second, purpose-built authoring surface is added next to it.

## Where it loads

**Property Setup → Specials → Partner offers** (a third sub-tab alongside Accommodations and Vouchers).

Specials is a shared section, so the same editor appears in both places with no duplicate code:

- ROL'OS → Setup Property → Specials → Partner offers
- Admin → Edit property → Specials → Partner offers

Non-ROL'OS properties (NightsBridge, Hostfully, Benson, manual) get the identical tab — perks are ROL-side guest content and do not depend on the connected system.

## What the property captures per offer

- Partner name and offer title
- Description of what the guest receives
- How to redeem (show brochure, present code at venue, contact partner)
- Optional redemption code — only if the partner supplied a real one. No code is generated by ROL.
- Optional partner link and contact
- Optional image
- Validity window and whether it is limited to a number of bookings
- Active toggle, plus which stays qualify (all stays, or minimum nights)

## Where the guest sees it

Revealed only after payment — a surprise, never a checkout line item:

1. **Journey brochure PDF** — its own "With compliments" block per qualifying property, alongside (not instead of) any real promo voucher block.
2. **Confirmation email** — a perks section listing each qualifying offer with redemption wording.
3. **Guest portal / journey view** — same list once the booking is paid or confirmed.

Not shown at checkout, not shown in price breakdowns, and it never changes any total. Unpaid or pending bookings show nothing.

TOBI keeps its existing rule: it may mention a perk that exists, and it still never invents a code.

## Technical notes

- New table `public.property_partner_offers`: `property_id`, `partner_name`, `title`, `description`, `redemption_instructions`, `redemption_code` (nullable), `partner_url`, `partner_contact`, `image_url`, `valid_from`, `valid_until`, `max_redemptions`, `current_redemptions`, `min_nights`, `is_active`, timestamps + `updated_at` trigger. GRANTs: `SELECT` to `anon` and `authenticated` (guest surfaces read active offers), full CRUD to `authenticated` gated by the same property-scope policy shape `promo_codes` uses, `ALL` to `service_role`.
- New `src/components/property/PartnerOffersTab.tsx` (mirrors `PromoCodesTab` structure: react-query list, dialog form, delete confirm). Wired into `src/pages/PropertyForm.tsx` under `specialsCategory === "partner-offers"` with a new `TabsTrigger`, so both surfaces pick it up.
- New shared helper `supabase/functions/_shared/partner-offers.ts` → `fetchQualifyingPartnerOffers(supabase, propertyIds, nights)`: active, inside validity window, under `max_redemptions`, `min_nights` satisfied. Returns `[]` when nothing qualifies so every render site collapses cleanly.
- `generate-itinerary-pdf`: add a perks block per property using that helper; leave `resolveRealVoucher` untouched.
- `send-booking-email`: add a perks section, rendered only when the booking is paid/confirmed and the helper returns rows.
- Guest portal/journey read path uses the same filter client-side against the table.
- No change to `validate-voucher`, `promo_codes`, pricing, rate resolution, or any total.
