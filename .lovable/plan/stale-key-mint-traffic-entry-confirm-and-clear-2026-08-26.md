# Stale key-mint traffic entry — confirm and clear

## What the pasted entry shows

The request body you pasted authenticates with a portal username/password and orders the
fields `Scope` then `Label`:

```text
<Authentication><UserName>…</UserName><Password>…</Password></Authentication><Scope>XmlApi</Scope><Label>ROLOS</Label>
```

The current code cannot produce that shape:

- `supabase/functions/_shared/ruApiKeyXml.ts` accepts key-pair auth only (there is no
  password branch left) and emits `Authentication` → `Label` → `Scope`.
- `supabase/functions/rentalsunited-api/index.ts` (`create_child_api_key`) refuses the call
  with `RU_FIRST_API_KEY_REQUIRED` when the resolved child auth is not a key pair, so no
  password-mode request reaches the channel.

So this is almost certainly a log row recorded before the fix was deployed, surfaced by the
Live Channel Traffic monitor with no response payload retained. It is not proof of a live
password-mode call — but that must be verified, not assumed.

## Plan

1. **Confirm the entry is historic.** Look up trace `75cceb7c-bb36-4536-9720-8315c4ee3e76`
   in the channel API log table and read its timestamp, owner/account scope and function
   version, then compare against the deploy time of the corrected `rentalsunited-api`.
   - If it predates the fix: nothing to change in behaviour; continue with steps 3–4.
   - If it postdates the fix: the deployed function is stale — redeploy `rentalsunited-api`
     and `ru-cert-portal` and re-check for new entries of this shape.

2. **Make the shape impossible to emit again.** Add a runtime guard in
   `buildCreateApiKeyXml` that throws if the auth object is not a `keys` pair (type-level
   only today, so a loose `as` cast at a future call site could reintroduce it), plus a test
   asserting the built XML never contains `<UserName>` or `<Password>`.

3. **Label stale traffic in the monitor.** In the Live Channel Traffic frame, mark rows
   older than the current adapter contract (no retained response, password-mode auth on
   `Push_CreateApiKey_RQ`) as `legacy — pre-fix shape` so a historic row is not read as a
   live failure.

4. **Verify.** Re-open the traffic monitor and confirm the only `Push_CreateApiKey_RQ`
   entries going forward carry `AccessKey`/`SecretKey` auth in `Label` → `Scope` order, and
   that accounts without a stored first key surface the guided first-key capture prompt in
   Step A instead of any outbound call.

## Technical notes

- Files touched: `supabase/functions/_shared/ruApiKeyXml.ts` (+ its two tests),
  `src/components/admin/channel-monitor/LiveTrafficFrame.tsx` (row labelling only).
- No change to the locked child-auth path semantics: first key pair is still captured
  manually from the channel portal, and rotation via `Push_CreateApiKey_RQ` still requires
  an existing verified pair.
- Redeploy is conditional on step 1's finding; no channel traffic is generated by the
  investigation itself.
